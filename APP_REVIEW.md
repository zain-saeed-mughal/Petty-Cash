Petty Cash Flutter app review — 18 September 2026

The current app should not be released with real expense data until the authorization, credential handling, financial-record deletion, and platform permission issues below are resolved.

Scope: all 35 Dart files under lib, all three test files, both root diagnostic scripts, the supplied SQL schema, dependency configuration, and Android/iOS/web/Windows configuration. This review includes existing uncommitted work. Application source and database records were not changed. The deployed Supabase schema, policies, RPC implementations, account configuration, and native device behavior were not inspected; database findings refer to the supplied schema and client code.

Verification:

- `flutter analyze --no-pub`: failed with 38 issues: 12 errors, 10 warnings, 16 informational findings. All 12 syntax errors are in the two root diagnostic scripts; they do not establish an application-entry-point compilation failure.
- `flutter test --no-pub test/petty_cash_test.dart test/widget_test.dart`: two model tests passed; the app smoke test failed with a null-client exception in AuthService.restoreSession.
- Two isolated widget probes confirmed that an Admin whose canApproveRequests is false still sees Approve & Pay / Reject, and that the expense form accepts both NaN and Infinity. These probes made no database calls.
- `flutter build web --no-pub`: passed; release output generated under build/web in 131.6 seconds. The Wasm compatibility dry run also passed. This is compilation verification, not a deployed end-to-end or native-device test.
- The live super-admin seeding test and both database-write diagnostic scripts were intentionally not executed.

P1 means fix before release. P2 means a material correctness or reliability defect.

1. **[P1] Authenticated users can change roles and anyone's expenses.** [Users policy](<C:/Users/DEV-BT/Desktop/Petty Cash/supabase_schema.sql:16>) and [requests policy](<C:/Users/DEV-BT/Desktop/Petty Cash/supabase_schema.sql:40>) permit every operation with unconditional true checks. With these policies deployed, an ordinary staff account can promote its own role, read other employees' requests, change amounts/status/audit logs, and delete records through the API. The provider already downloads all requests and filters ownership on the client. Enforce ownership, role, active-account status, permitted columns, and transitions in the database. This is a confirmed defect in the supplied policy definitions, not a claim that live policies were tested. [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).

2. **[P1] Passwords are serialized into profiles and displayed to administrators.** [AppUser.toMap](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/models/user_model.dart:90>) includes the password; fromMap reads it back, profile updates write it, and [user cards](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/admin/user_management_screen.dart:522>) display it without masking. If the live profile schema supports this field, profile readers can obtain credentials; the supplied SELECT policy allows all authenticated users to read profiles. Remove password persistence and display; use Supabase Auth for credential changes. If actual passwords have already been stored, remove those values and reset affected credentials. If the supplied schema is used unchanged, this instead produces the schema error in finding 3.

3. **[P1] The checked-in backend setup cannot support the current app.** [Database service](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/services/database_service.dart:137>) calls admin_create_user, update_user_credentials, and delete_user, but none is defined in [the SQL setup](<C:/Users/DEV-BT/Desktop/Petty Cash/supabase_schema.sql:4>). The notifications table is also absent. AppUser.toMap always sends a password key, including null, while users has no such column. The add-user fallback supplies an empty UUID and cannot create an auth.users record. A fresh database created from this repository cannot complete the current user-management flows. Include versioned migrations, restricted RPC definitions, notifications policies, and provisioning instructions; remove password from profile serialization rather than adding a plaintext password column. Realtime publication setup is also absent, while all mutation refreshes depend on streams; new tables do not enable Realtime automatically. [Supabase stream documentation](https://supabase.com/docs/reference/dart/stream).

4. **[P1] Suspended accounts are still accepted.** [Sign-in profile handling](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/services/auth_service.dart:61>) and [session restoration](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/services/auth_service.dart:29>) never reject isActive == false. The administration switch explicitly promises access suspension, but login/routing and the supplied RLS policies ignore that flag. Block inactive accounts at the backend and client, and refresh/revoke existing access when a role or active status changes.

5. **[P1] Admin users can reach finance approval actions through normal navigation.** [Review actions](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/finance/request_detail_screen.dart:389>) depend only on the request being Pending. Admin can navigate there from [Review Detail](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/admin/all_transactions_screen.dart:426>) or reports. The handlers check only that a user exists, and the provider does not check canApproveRequests. An isolated widget probe confirmed both action buttons are present for a non-approving Admin. Enforce the same permission in UI, action handlers, and the backend.

6. **[P1] Deleting an employee also deletes their financial history.** [requestedBy foreign key](<C:/Users/DEV-BT/Desktop/Petty Cash/supabase_schema.sql:21>) uses ON DELETE CASCADE. Both deleting the public profile and deleting its parent auth record can erase every request and its embedded audit history, including paid expenses. The account-removal dialog only describes removing the account. Preserve financial rows using restricted deletion or retained/inactive profiles and an explicit retention model.

7. **[P1] Concurrent reviews can overwrite status and audit history.** [Approval](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/providers/expense_provider.dart:246>) and rejection copy a locally cached request and append to a locally cached log list. [updateRequest](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/services/database_service.dart:97>) then replaces all columns by ID without an expected-status/version condition. Two reviewers can both act on Pending, with the later write erasing the earlier decision and log. The detail screen also keeps its original request snapshot. Use one transactional backend transition with a status/version precondition and an append-only audit record, and react to current request state in the UI.

8. **[P1] Receipts are served publicly.** [Bucket configuration](<C:/Users/DEV-BT/Desktop/Petty Cash/supabase_schema.sql:44>) explicitly creates a public receipts bucket, and [the upload service](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/services/storage_service.dart:50>) returns permanent public URLs. Anyone possessing a URL can retrieve the receipt without logging in. Use a private bucket with ownership/role policies and authorized downloads or short-lived signed URLs. [Supabase bucket access model](https://supabase.com/docs/guides/storage/buckets/fundamentals).

9. **[P1] Android release is missing internet access.** The [main manifest](<C:/Users/DEV-BT/Desktop/Petty Cash/android/app/src/main/AndroidManifest.xml:1>) contains no INTERNET permission; it exists only in debug/profile manifests. The available debug manifest-merger report identifies the debug manifest as its source, and the installed plugin main manifests do not supply it. Release requires this permission to reach Supabase and receipt URLs. Add it to the main manifest and verify the merged release manifest on an Android build.

10. **[P1] iOS receipt capture lacks required privacy descriptions.** [Info.plist](<C:/Users/DEV-BT/Desktop/Petty Cash/ios/Runner/Info.plist:4>) has neither NSCameraUsageDescription nor NSPhotoLibraryUsageDescription, while the app exposes camera and gallery access. Camera use can terminate the app when the required description is absent. Add the usage descriptions and exercise picking/capture on a real iOS device. This finding is based on configuration, not an iOS execution here. [Official image_picker setup](https://pub.dev/packages/image_picker).

11. **[P1] The default test suite contains live privileged-account provisioning.** [seed_superadmin_test](<C:/Users/DEV-BT/Desktop/Petty Cash/test/seed_superadmin_test.dart:7>) targets the same configured Supabase project as the app, uses embedded default credentials, and attempts to create/upsert a super-admin. Ordinary `flutter test` discovers this file. Exceptions are mostly printed instead of failing assertions, so failure may even appear successful. Move provisioning outside automatic tests, require an explicitly selected disposable environment, and remove embedded credentials. Rotate the default credentials if that account was provisioned.

12. **[P2] Credential-edit failure can be reported as success.** [updateUser](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/services/database_service.dart:155>) commits the public profile before updating auth credentials, then catches and suppresses RPC failures. If the RPC fails or rejects an email/password, the UI announces success while login still uses the old credentials and profile information disagrees. Route the operation through a secured backend operation with consistent failure handling and return a failure when credentials did not change.

13. **[P2] Initialization failure leaves session restoration stuck.** [The client getter](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/services/auth_service.dart:16>) force-unwraps an unavailable client before restoreSession's try block. SupabaseService catches initialization failures and continues, but RoleRouter/AuthProvider have no finally/error path to clear their loading states. The existing smoke test reproduces the null exception. Handle unavailable initialization explicitly and always finish loading with a visible recovery action.

14. **[P2] Expense/user subscriptions survive account changes.** [Root providers](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/main.dart:34>) create ExpenseProvider/UserProvider for the app lifetime; only NotificationProvider follows AuthProvider. The first two subscribe once, never clear their caches at sign-out, and never refetch for a replacement user. After a failed/closed stream or after tightening RLS, signing in again can leave stale or empty data from the previous session. Scope these providers to the authenticated identity, cancel subscriptions, clear sensitive state, and refetch on login.

15. **[P2] History and totals become incomplete when the API row cap is reached.** [streamAllRequests](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/services/database_service.dart:55>) uses one unpaginated stream, and reports/analytics compute totals from that result. The installed Supabase stream implementation uses a single initial SELECT. Supabase's default response cap is 1,000 rows, so older requests and their totals disappear once the configured cap is exceeded. Use paginated/filterable history and server-side aggregate queries; do not treat one response as the entire ledger. [Supabase SELECT limits](https://supabase.com/docs/reference/dart/select).

16. **[P2] Invalid non-finite amounts pass validation.** [Amount validator](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/office_boy/new_request_screen.dart:256>) accepts NaN and Infinity because parsing succeeds and the <= 0 check does not reject both cases. Both were reproduced in an isolated widget probe. Encoding a non-finite amount into the request can then fail instead of presenting a field error. Require a finite positive amount, define currency precision, and enforce the equivalent database constraint.

17. **[P2] Approved/paid filters omit Approved requests.** [My Requests](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/office_boy/my_requests_screen.dart:148>), [All Transactions](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/admin/all_transactions_screen.dart:242>), and [Payment History](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/finance/payment_history_screen.dart:140>) label the filter as both statuses but select only RequestStatus.paid. The count includes Approved, yet the selected list excludes those rows. Filter by a set of the two statuses or provide separate filters.

18. **[P2] Leaving a screen during an async operation can trigger setState after dispose.** [Submission](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/office_boy/new_request_screen.dart:115>) updates state after uploads/network calls before checking mounted. [Review actions](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/finance/request_detail_screen.dart:69>) do the same. Switching away from New Request during submission or backing out of a review on a slow connection can trigger a lifecycle exception, even if the write succeeded. Check mounted immediately after awaits before accessing state/controllers/context, and use finally for operation-state cleanup.

19. **[P2] Disbursed/settled totals include unpaid Approved requests.** [totalSpent](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/providers/expense_provider.dart:140>) includes Approved and Paid, but consumers label it TOTAL DISBURSED or Total Settled / Paid. Approved is separately representable through the override UI and model, so these labels can overstate actual paid funds. Calculate paid and approved commitments separately, or explicitly change the status model and labels if approval always means payment.

20. **[P2] Requester analytics merge different people with the same name.** [Analytics grouping](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/super_admin/analytics_screen.dart:370>) keys totals by requesterName. Two employees sharing a name are merged; a renamed employee is split across stored names. Group by requestedBy UID and choose the display name separately.

21. **[P2] Data errors are shown as legitimate empty results.** [Pending screen](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/finance/pending_requests_screen.dart:124>) and the other list/report screens do not render ExpenseProvider.isLoading/errorMessage. A failed first load therefore shows All Caught Up / No Transactions, while analytics displays zero values. Approval/rejection failure also lacks visible feedback in RequestDetailScreen. Add distinct loading, error/retry, empty, and success states so staff do not act on a failed load as if it were an empty ledger.

22. **[P2] Root diagnostic scripts fail repository analysis.** [test_supa.dart](<C:/Users/DEV-BT/Desktop/Petty Cash/test_supa.dart:25>) and [test_supa2.dart](<C:/Users/DEV-BT/Desktop/Petty Cash/test_supa2.dart:27>) contain unterminated print strings, generating 12 syntax errors. Fix/remove obsolete scripts or deliberately isolate them from production checks. Do not execute their live writes as part of lint cleanup.

Additional issues and decisions to resolve:

- [Storage fallback](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/services/storage_service.dart:52>) silently stores a base64 image in a database text field when upload fails. This enlarges every request-list payload, hides the storage failure, and is incompatible with the detail screen's HTTP image loader on native platforms. The full-screen receipt dialog handles base64, but the [embedded detail preview](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/finance/request_detail_screen.dart:347>) does not. Prefer explicit upload errors/retry and a consistent receipt renderer.
- [Admin navigation](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/admin/admin_dashboard.dart:39>) offers no user-management destination although AppUser.canManageUsers and the management UI allow Admin to manage Finance/Office Boy. Confirm whether this was intentional; otherwise restore the entry point.
- [Monthly reporting](<C:/Users/DEV-BT/Desktop/Petty Cash/lib/screens/reports/monthly_reporting_screen.dart:46>) groups paid amounts by the request's creation month. A request created in August and paid in September is counted under August. Decide whether this is a submission-cohort report or cash movement report; the latter needs a persisted paidAt field. User/status filters change table rows while KPI totals remain for all users/statuses; labels should make that scope explicit or follow the filters.
- Date serialization uses local DateTime.now().toIso8601String() without a timezone offset for database timestamptz fields, and received timestamps are not consistently converted for display. Standardize UTC persistence and the reporting/display timezone before relying on month-boundary totals.
- Request IDs retain only eight hex characters from a UUID. Use the full UUID as the primary key and a separate short display reference to avoid eventual collisions.
- Image upload UI advertises 10 MB but no byte limit is enforced. Every upload is named/type-tagged JPEG regardless of original file encoding. Enforce byte limits and accurate content types; gate the Windows camera button on actual supported camera capture.
- [Release Android signing](<C:/Users/DEV-BT/Desktop/Petty Cash/android/app/build.gradle.kts:36>) still uses the debug signing configuration. Configure the intended release/upload key before distribution.
- README contains only Flutter starter instructions. Add environment setup, database migrations, secured administrator provisioning, safe test commands, supported platforms, and release instructions.

Suggested repair order: secure database permissions and credentials; make backend setup reproducible; preserve the ledger and enforce atomic transitions; repair auth/session handling and platform permissions; correct reports/filters/error states; then add authorization, concurrency, account-switching, database-contract, and device integration coverage.
